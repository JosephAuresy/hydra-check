What this is (and what it is not)

This tool does not replace the official Google Groups — it is a structured, instant, private front-end to the knowledge those communities have already produced. The groups remain the source of truth and the place for genuinely hard questions. What this tool does is take the documentable majority of problems — the same procedural and configuration errors that get asked hundreds of times — and answer them in seconds, offline, while routing everything else back to the community with a better-formed question.

Design principle: never manufacture false confidence. When a problem falls at a framework's complexity frontier (boundary-condition conceptualization, SW–GW exchange behavior, joint-calibration judgment), the correct behavior is to scope the question and defer to a human expert — not to guess.

What gets resolved here — and what doesn't

Every category below is classified by its nature — the same procedural/theoretical axis the underlying taxonomy uses — with the real number of coded threads and, where extracted, the real community resolution rate alongside it as supporting evidence.

Why you can trust a free tool

Every finding is traceable
Each rule maps to a taxonomy category derived from real, coded community threads — not a black-box guess. You can see why a finding fired and which community it comes from.
Community knowledge is attributed, never copied
Recurring solutions are re-expressed in the authors' own words and attributed at the community level (e.g. "as commonly advised in the SWAT-MODFLOW group"). No verbatim posts are reproduced — contributors are acknowledged, not appropriated.
It admits what it doesn't know
Frontier questions are flagged for expert review instead of answered with confident-sounding but unreliable advice.

Where this is going — and why it will beat a generic AI notebook

This diagnostic tool is Tier 1 of a two-tier design. Tier 2 adds a retrieval-grounded assistant on top, without weakening what Tier 1 already guarantees.

Tier 1 — deterministic rules (live today)

File/error signatures extracted from the high-frequency procedural & configuration categories of the taxonomy. Zero hallucination risk — every rule is a fixed pattern match, and every finding names the exact file/line that triggered it.

Tier 2 — grounded assistant (planned)

A retrieval-augmented layer over (a) official documentation and manuals (SWAT+, MODFLOW 6/USGS PDFs) and (b) the synthesized, attributed experiential knowledge mined from these same communities — for the long tail of questions Tier 1's fixed rules don't cover. It answers from that grounded knowledge base only, cites its source, and explicitly defers when a question falls at the complexity frontier instead of improvising an answer.

Why that will be more useful than pointing a general tool (e.g. NotebookLM) at the same PDFs and forum exports:

Methodology — how the knowledge base was built

  1. Corpus. ~9,100 user-reported threads from the four official communities (SWAT-user, SWAT+ groups, SWAT-MODFLOW, MODFLOW users), 2009–2026. De-duplicated; announcements and pure acknowledgements removed. Automated retrieval respects each platform's terms of service.
  2. Grounded-theory coding (3 passes). Open coding tags recurring problem statements; axial coding groups them into higher-level categories; selective coding consolidates a stable, model-agnostic taxonomy (T-CAT: 12 categories across 6 domains).
  3. Four-way nature classification. Each thread is labelled Procedural (a documented fix exists), Theoretical (needs hydrological reasoning, no single answer), Configuration (environment/version/paths), or Software bug — using explicit, auditable decision rules. The procedural↔theoretical axis is the one that decides whether documentation can resolve a problem.
  4. Reliability. A stratified gold-standard sample is coded by hand and used to measure inter-/intra-coder agreement (Cohen's κ) and the accuracy of the automated classifier — reliability is treated as a result, not an afterthought.
  5. Taxonomy → rules. The high-frequency procedural/configuration categories have deterministic error signatures — file patterns (null soil fields, low file-unit numbers, period mismatches) and log strings (error 65, forrtl 157, non-convergence). These signatures became the rules in this tool. The high-theoretical frontier categories are deliberately excluded from automation.

Reproduce this for another model community

The pipeline is open and model-agnostic. To apply it to any technical forum (HEC-HMS, ParFlow, a private tool's issue tracker…):

  1. Scrape thread metadata + first post (scraper/scrape_groups.py).
  2. Keyword open-coding + axial voting (scripts/02_code.py).
  3. LLM fallback for the hard remainder, with few-shot examples and independent nature judgment (scripts/03_llm_code.py).
  4. Build a stratified gold sample and validate (scripts/06…08); report κ and accuracy.
  5. Extract error signatures for the procedural/config majority; keep frontier categories as deferral, not automation.

Full coding scheme, decision rules and taxonomy definitions are released so the scheme can be re-applied and audited. Part of the SWAT Issue Atlas — an open, reproducible pipeline for longitudinal community-health monitoring.

Limits (read before relying on it)

Reported difficulty ≠ total difficulty
Forums over-represent problems users couldn't solve alone. Silent, self-resolved issues are under-represented.
Signatures cover the documentable majority, not everything
A clean result here means no known signature fired — not a guarantee your model is correct.
Active platforms drift
Issue profiles shift as software matures (e.g. SWAT+). The pipeline is designed to be periodically re-run so the knowledge base stays current.
